When people learn Git for the first time, the hardest part usually is not the number of commands. It is the lack of context.

You may already know that `git init` creates a repository, `git add .` stages files, and `git commit -m "..."` saves a snapshot. But once those commands enter a real project, a new set of questions appears immediately:

- How complete should the first commit be?
- Which files should go into the repository, and which ones should stay out?
- How do you write commit messages that still make sense later?
- After writing a post or tweaking a layout, how should Git fit into the publishing workflow?

Instead of using an empty demo folder, this article uses my actual blog repository as the example.

It is a personal blog built with **Astro** and deployed to **GitHub Pages**. That makes it a better teaching case than a fake toy project, because you can see not just what Git can do, but how Git is actually used inside a growing project.

If you want the site-building side first, read: [Build an Astro blog from scratch and deploy it to GitHub Pages](../build-astro-blog/).

## Start with the commit history

Here are a few representative commits from the repository:

```text
01237d2 first commit
9229bac readme
8a50a72 chore: keep repo clean and enforce PR workflow
3e61e81 feat: rebrand site and add author profile links
85684eb fix: correct post link and widen article layout on pages
467248e style: keep centered layout and shift toc left only
12bad23 feat: use provided avatar image
```

Even a short list like this already tells a story:

- `first commit` captures the starting point
- `readme` improves project documentation
- `chore` keeps the repository clean
- `feat` adds visible functionality
- `fix` corrects a problem
- `style` refines presentation without changing behavior

That is where Git becomes valuable. It preserves the path a project took, not just the latest result.

## Your first commit does not need to be perfect

This blog also began as a freshly created Astro project. A typical starting flow looks like this:

```bash
npm create astro@latest my-blog -- --template blog
cd my-blog
git init
git status
git add .
git commit -m "first commit"
```

Many beginners hesitate here: "The project still feels rough. Should I wait?"

My answer is no.

The value of a first commit is not that it finishes the project. It captures **the first working version**. Later, if you break a layout, delete a component by mistake, or simply want to see where the project started, that snapshot becomes useful immediately.

In this repository, the first entry really was:

```text
01237d2 first commit
```

It is plain, but it does the most important job: it preserves the starting point.

## `git status` is the habit worth building first

If there is one Git command that deserves repetition, it is not `git commit`. It is:

```bash
git status
```

Many Git mistakes happen not because people cannot commit, but because they do not know what they are about to commit.

`git status` works like a dashboard. It shows:

- Which files changed
- Which files are already staged
- Which files are still untracked

In this blog project, I rely on it at three moments:

1. Before I start editing, to confirm the working tree is clean
2. Before I commit, to confirm I am not including unrelated files
3. Before I push, to make sure the change is actually ready to go out

That habit prevents very ordinary mistakes:

- Accidentally committing a local test file
- Forgetting that a config file changed
- Intending to publish one post but also shipping unrelated experiments

If you are still building Git habits, start here: run `git status` before every commit.

## Not every file belongs in the repository

This blog also went through a classic early-project mistake.

In the first phase, some local files generated by development tools ended up in the repository together with the source code. That included caches, logs, and tool state. Later I had to clean them up with a dedicated commit:

```text
8a50a72 chore: keep repo clean and enforce PR workflow
```

That commit is useful because it is not about a shiny new feature. It is about making the repository healthier for long-term work.

The current `.gitignore` excludes things like:

```text
dist/
node_modules/
.astro/
.omc/
.vite-temp/
.vite-cache-*/
dev*.log
dev*.err
AGENTS.md
CLAUDE.md
```

You can think of the rule in two groups.

Files that usually belong in Git:

- Source code
- Content files
- Configuration
- Deployment workflows

Files that usually do not:

- Dependency directories
- Build output
- Caches
- Logs
- Local tool state

Good repository hygiene is not about committing everything. It is about committing the right things.

## Commit messages decide whether future-you can read the history

One of the most underestimated parts of Git is the commit message.

Almost everyone starts with vague messages like these:

```text
change
try again
fix
update
move toc
```

They work for a few minutes because you still remember what happened. A few weeks later they become almost useless.

Later commits in this repository became much clearer:

```text
feat: rebrand site and add author profile links
fix: correct post link and widen article layout on pages
style: keep centered layout and shift toc left only
chore: keep repo clean and enforce PR workflow
```

This style helps because each message answers two questions:

1. What kind of change is this?
2. What did the change roughly do?

For a personal project, a small set of prefixes is often enough:

| Prefix | Use case |
|------|------|
| `feat` | New feature, page, or interaction |
| `fix` | Bug fix or behavior correction |
| `style` | Visual or layout-only adjustment |
| `docs` | Documentation or blog content update |
| `chore` | Maintenance, cleanup, or config work |

For example, if you only publish a new article, this:

```bash
git commit -m "update"
```

is much less helpful than this:

```bash
git commit -m "docs: publish git tutorial for my blog"
```

The exact wording can vary. The important part is that the message stays understandable later.

## A good commit should usually do one thing

Another Git principle that matters more than people think is this: keep each commit focused.

Imagine you do three things in one session:

- Write a new article
- Adjust page spacing
- Replace an avatar asset

You can commit them all together, but that makes the history harder to read, and it makes future rollback harder too.

A cleaner flow is to split the work. For example:

```bash
git status
git diff
git add src/content/blog/git-guide-with-my-blog.md
git diff --staged
git commit -m "docs: publish git tutorial for my blog"
```

The key idea is that `git add .` is not always the best choice.

It is convenient, but it can easily sweep unrelated changes into the same commit. If you already know the specific file, component, or style update you want to commit, stage that directly.

Focused commits create clearer history and safer reversions.

## Git also helps you understand how the project became what it is

One reason I like revisiting commit history is that it restores development context I have already forgotten.

Looking only at the history of this blog, you can already see a rough progression:

1. Build the first working version with `first commit`
2. Add a `README`
3. Notice that logs and caches leaked into the repo, then clean them up
4. Keep refining the article layout, table of contents, and typography
5. Rebrand the site more clearly around a personal identity
6. Replace placeholder visuals with the real avatar

At that point Git stops being just a backup tool. It becomes the timeline of the project.

If you want a better view of that history, use:

```bash
git log --oneline --graph --decorate
```

If you want to inspect a single commit in more detail:

```bash
git show 3e61e81 --stat
```

That is often much more reliable than trying to remember whether you changed a file last week or last month.

## In this project, `git push` is almost the same as "ready to publish"

This repository is useful for learning Git because Git is not only local version control here. It is also part of the publishing pipeline.

The site uses a GitHub Pages workflow:

```text
.github/workflows/deploy.yml
```

Whenever the `main` branch receives a push, GitHub Actions builds and deploys the site. In practice, the workflow usually looks like this:

1. Change content or code
2. Run `git status`
3. Stage the intended files
4. Commit the change
5. Run `npm run build`
6. Push with `git push origin main`
7. Wait for deployment to finish

That is why Git now feels like part of the blog workflow instead of an extra task around it.

## A simple Git routine for a personal blog

You do not need a complicated Git strategy for a personal blog. Simple, readable, and stable is enough.

Here is a workflow I would recommend:

### When writing a new post

```bash
git status
git add src/content/blog/new-post.md
git commit -m "docs: publish a new blog post"
npm run build
git push origin main
```

### When fixing a layout problem

```bash
git status
git add src/components src/layouts src/styles
git commit -m "fix: improve post layout on small screens"
npm run build
git push origin main
```

### When tuning styles

```bash
git status
git add src/styles/global.css src/layouts/BlogPost.astro
git commit -m "style: rebalance article width and toc spacing"
npm run build
git push origin main
```

These commands look similar on the surface, but two details make the difference:

- The staged scope is explicit
- The commit message stays readable

If you keep those two habits, your Git history is usually in pretty good shape.

## Closing thought

Git can feel dry when it is taught only as a list of commands. But inside a real project, it does something much more concrete:

1. It preserves each stage of work
2. It explains why changes exist
3. It makes future edits safer

That is why this blog repository is such a good example. The article you are reading now only exists because the project history stayed readable enough to revisit and turn into a tutorial.

If you are just starting with Git, you do not need every command at once. Start with the important habits:

- Check status
- Stage intentionally
- Write understandable commit messages
- Build before you push

Use Git that way for a while, and it stops feeling like memorization. It starts feeling like part of how you work.
